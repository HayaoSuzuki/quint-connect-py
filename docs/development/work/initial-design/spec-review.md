# Quint 仕様のレビュー

[再生モデル](../../../../spec/quint_connect.qnt) は複数の API 呼び出しの進行を表す。各呼び出しが選んだ操作パスと状態パスを固定し、CLI の計画、検証済みステップ、ドライバーの操作と観測、不一致の診断を記録する。共有のファイル状態では、作業先と保存先の所有関係を追跡する。

## 境界

| モジュール | 形式化した契約 | 実環境で確認する境界 |
| --- | --- | --- |
| [CLI](../../../../spec/quint_cli.qnt) | 実行ファイルの指定、モードごとの引数と既定値、符号なし 64 ビット seed、生成件数とサンプル・ステップの境界（最大値は JavaScript の安全な整数の上限）、名前付きテストの完全一致、出力項目の種別・名前による選別と数値順、呼び出し元を基準にしたモデルと実行ファイルのパス、子プロセスの作業先、各 OS 引数の境界と文字列・数値の表記 | OS の文字・パス表現、ディレクトリ項目の分類、子プロセスの実行と終了結果 |
| [PATH 探索](../../../../spec/quint_path_search.qnt) | 候補順、最初の実行可能候補、探索した範囲、全候補が使えない場合の診断 | ホスト OS での実行可否の判定と実行ファイル名の規則 |
| [UTF-8 と JSON](../../../../spec/quint_json.qnt) | UTF-8 の正当性、Unicode エスケープ、数値・文字列・リテラルの字句、配列とオブジェクトの構文、重複した項目を保持する節点列 | Rust のデコーダーが同じバイト列を受理・拒否すること |
| [ITF](../../../../spec/quint_itf.qnt) | 展開済みの同名キー、エンベロープと宣言変数、操作の取得元と匿名操作の空文字列、選択パス、`#bigint` の十進構文、引数直下の `Some`・`None`、最初の不正ステップ、操作名・引数名・選択パスのコードポイント比較 | Rust のデコーダーと PyO3 の文字列変換 |
| [複合値](../../../../spec/quint_values.qnt) | 型を区別した等値性、反射律・対称律・推移律、順序付きのリストとタプル、順序に依存しない集合とマップ、任意精度の整数と正規化、等価な集合要素の統合、複合キーの重複 | Rust の値表現と Python の値との変換 |
| [ファイルシステム](../../../../spec/quint_filesystem.qnt) | 一意な作業先、成果物ディレクトリの排他的な確保と候補名衝突、終了失敗後の部分出力、専用ディレクトリに残るファイル・リンク・ディレクトリ・特殊ファイル、コピー中と全バイト書き込み後の非公開状態、公開失敗、公開前後の並行読み取り、元バイト列の保存、別名の解決と循環の検出、掃除の対象範囲と部分失敗 | OS でのパスの解決、ディレクトリの排他的確保、OS の I/O エラー、ファイルの公開と削除 |
| [再生と診断](../../../../spec/quint_connect.qnt) | CLI 設定の検証・実行ファイル選定・作業先確保の順序と診断に残す seed、起動失敗・非ゼロ終了・シグナル終了・待機と回収の失敗、終了確認前の掃除の保留、CLI 正常終了後の一覧取得と生成ファイルの読み取り、それぞれの失敗と診断、呼び出し元を基準にした保存済みパスと成果物の親、読み取り順と診断、検証後のドライバー生成、コールバックによる引数の変更と元の診断、最初の不一致、保存後の同一バイト列からの再生 | pytest-xdist の実プロセス間分離、PyO3 を通した例外の型・属性・元の原因 |

JSON と複合値は、子を親より先に置いた有限の節点列で表す。JSON の文字とオブジェクトのキーは、UTF-8 やエスケープを展開したコードポイント列で表す。JSON 数値は文法を検査し、節点には数値であることを記録する。ITF の値として選んだ整数は `#bigint` の文字列から読む。ITF 入力では先頭の BOM と、対になっていないサロゲートのエスケープを拒否する。[RFC 3629 §4](https://www.rfc-editor.org/rfc/rfc3629#section-4) · [RFC 8259 §8](https://www.rfc-editor.org/rfc/rfc8259#section-8)

生成された ITF と、利用者が指定したパスの ITF は、同じ関数でバイト列を UTF-8、JSON、ITF の順に検証する。保存した成果物のパスも、利用者が指定したパスとして同じ手順で読み取る。デコードした Unicode スカラー値の列を、操作名、引数名、選択パス、文字列値の比較まで使う。文字を直接書いた場合とエスケープで書いた場合は同じ列になる。異なる列を持つ文字列は区別する。Rust でも同じコードポイント列を表す文字列を比較する。

CLI コマンドは、呼び出し元に結び付けたモデルと実行ファイルのパス、および子プロセスの作業先の識別子を保持する。引数列では、オプション名と値を等号でつないだ文字列を一つの要素とする。seed と件数は十進表記にし、名前付きテストの選択には正規表現の特殊文字をエスケープする。名前だけの実行ファイルは、呼び出し元の `PATH` を順に調べる。候補の実行可否は外部から与え、選ばれた候補を起動計画に記録する。保存済み ITF を開くパスと成果物の親ディレクトリにも、呼び出し元を基準としたパスを使う。具体的なパス文字列の組み立てや、シンボリックリンクを含むパスの参照先は OS の試験で確認する。

ファイルシステムは、パスの論理的な識別、確保した専用ディレクトリの排他的な所有、呼び出しの外からのファイル変更がない状態を前提とする。別名はパスの間の参照として扱い、読み取り時に参照をたどる。掃除は作業先に属する項目だけを削除する。私有ディレクトリはその内容を含む一単位として扱う。プロセスの終了を確認できず掃除を保留した場合は、観測した項目を保持する。クラッシュ時の永続性は OS 側の前提が必要となる。

Python 固有の契約として確認する項目は、例外の型、属性、元の原因に絞る。モデルが定める再生の振る舞いは公開 API から確認する。たとえば `StateMismatchError` の基底型は `AssertionError` で、トレース、ステップ、操作、期待値、実測値を読める。生成したトレースなら seed と保存先、または保存エラーを読める。ドライバーの例外は `__cause__` を確認する。配布とインストールは通常の受け入れ試験で確認する。[Rust 実装計画](plan.md)

## 不変条件

| 性質 | 検査すること |
| --- | --- |
| `replayInOrder` | 出力一覧から通常ファイルを選び、生成ファイルを順に読んでから検証する。検証済みトレースごとにドライバーを生成し、操作名・引数・期待値を該当ステップと照合し、コールバックによる引数変更後も元の値を診断に使う |
| `firstFailureStopsReplay` | 最初の失敗から保存・子の終了確認・掃除・結果の返却へ進む。保存済みパスの読み取りは先行 ITF の全ステップが一致した後に進む |
| `mismatchKeepsEvidence` | 記録された不一致、対象トレース、seed、保存の結果を診断に保持する |
| `consistentResult` | 成功には全トレースの検証と全ステップの一致を要求する。先行エラーと掃除失敗を保持する |
| `isolatedResources` | 予約した作業先とドライバーを呼び出し間で分離する。CLI の引数、seed と作業先を計画に照合する。作業先の確保失敗も同じ計画と seed に結び付け、一覧取得が正常終了に続くことと、起動済みの子の作業先は終了確認後に掃除することを検査する |
| `persistedEvidence` とファイル状態の不変条件 | 保存成功が元のバイト列を公開し、保存失敗が公開先を残さないことを確認する。保存先の確保は他の呼び出しの成果物を維持する。公開前には保存ファイルを開けず、公開後は作業先の掃除をまたいで読める |
| `processingProgress` | 各未終了段階で次の応答を受け取れること、各遷移で残り作業が減ること、全件終了時だけ残り作業がゼロになることを検査する |

残り作業は段階、残りトレース、残りステップなどを並べて表し、全呼び出しの成分ごとの和を辞書式順序で比較する。この順序なら、たとえば次のトレースのステップ数が増えても、残りトレース数が減れば全体の残り作業が減る。CLI、I/O、ドライバーの応答を受け取り、モデルの遷移を続けることが前提となる。子の終了が不明なまま掃除を保留した場合、保持された部分出力はその時点での観測を表す。

## 実行結果

Quint 0.34.0 で全モジュールを型検査し、Rust と TypeScript の両評価器でそれぞれ **162 件**のシナリオが通った。内訳は生成と再生 25 件、生成後の I/O と成果物公開 7 件、成果物ディレクトリの確保 5 件、保存済みパス 11 件、CLI 22 件、PATH 探索 6 件、起動計画 6 件、起動と終了 5 件、起動後の I/O と終了確認 7 件、引数のスナップショット 2 件、ファイルシステム 21 件、ITF 18 件、複合値 13 件、UTF-8 と JSON 10 件、四件の並行呼び出し 1 件、進行性 3 件。

固定リビジョンの公式 `tictactoe.qnt` を使い、Quint 0.34.0 の両バックエンドで `run --mbt --max-samples=1 --max-steps=12 --seed=0x2a` を実行した。得られた ITF のバイト列を `parseItfBytes` と `decodeItf` に渡し、13 状態の操作順と各ステップの引数件数を検証した。別の短いモデルでは、実際の `quint test` が生成した ITF から明示操作を読み取り、無名アクションを使う `quint run --mbt` の ITF から空の操作名を読み取った。[公式モデル](https://github.com/quint-co/quint-connect/blob/3b9eab8d817cbcd6de64ca1b05a20f18b96797ef/connect/examples/tictactoe/spec/tictactoe.qnt)

複合値のテストでは、集合・マップ・リスト・タプルを対象に、要素数 0 から 3 までの順列の組をすべて照合した。入れ子を含む有効な 30 個の値を組み合わせ、等値性の反射律・対称律・推移律を検査した。

各評価器で、二件の呼び出しは最大 48 ステップで 5,000 サンプル、四件の呼び出しは最大 96 ステップで 1,000 サンプル、ファイルシステム単体は最大 35 ステップで 1,000 サンプルを検査した。二件のモデルは、各サンプルで二件とも終了した。27 個の観測条件のうち、Rust で 25 個、TypeScript で 24 個に到達した。書き込みと公開成功は両評価器の四件モデルと個別シナリオで確認した。候補名の衝突は両評価器の個別シナリオで確認した。四件のモデルはすべての作業先を確保してから各呼び出しの処理を進め、各サンプルで四件すべてが終了した。この範囲で不変条件の反例は出なかった。

結合シナリオでは、最大 seed で生成を開始し、10 番より 2 番を先に読み、不一致になった ITF を元のバイト列のまま保存する。作業先を掃除した後、返された保存先を通常のパス指定に渡し、同じ操作と値の不一致をパス付きで再現する。別のシナリオで、名前付きテストの明示操作、違うファイルのバイト列、構文エラー、CLI が失敗したときの部分出力を検査した。四件を並行させたシナリオでは、seed・ファイル名・成果物の親ディレクトリが同じ状態で異なるバイト列を使い、コピーと掃除の一部が失敗しても他の呼び出しのファイルが残ることを確認した。

[生成後の I/O と成果物公開のシナリオ](../../../../spec/quint_runner_io_test.qnt)では、一覧取得の失敗と掃除の失敗が重なっても一覧取得の診断が残ること、二件目の読み取りに失敗すると、一覧で得た実際のファイル名と原因を保持して三件目を開かないことを検査した。公開前に開いた再生ではファイル未発見になり、公開前にパスを受け取って公開後に開いた再生では全バイトが読めた。全バイトを書いた後に公開だけが失敗した場合も、元の不一致を保持した。

出力一覧に通常ファイルと同じ形式の名前を持つディレクトリ、特殊ファイル、別の呼び出しの成果物を指すリンクを混ぜた。生成件数には通常ファイルだけが入り、作業先の掃除後も参照先の成果物が残った。掃除の部分失敗では、残存項目として報告されたディレクトリや特殊ファイルを保持した。終了を確認できなかった異常系では、掃除を保留して元のエラーと全種類の部分出力を保持した。進行性のシナリオでは次のトレースでステップ数が増える場合と、空のバイト列を保存する場合を確認した。[生成後の I/O](../../../../spec/quint_runner_io_test.qnt) · [進行性](../../../../spec/quint_progress_test.qnt)

## Rust 実装との照合

照合用の Quint シナリオ 15 件は、ITF のバイト列、I/O 結果、ドライバーの応答を再生モデルに与える。成功、壊れた ITF、ドライバー失敗、起動失敗、非ゼロ終了、シグナル終了、保存先確保の失敗、終了確認ができない待機失敗、出力回収に失敗した後に終了を確認する場合、引数変更後の不一致、匿名操作の引数と不一致診断に現れる複合値の正規化を含む。照合データのスキーマはバージョン 2 とし、入力に呼び出し ID と全体の実行順、出力に呼び出しごとの結果を持つ。従来の 10 ケースの入力と期待結果も同じ形で保持する。二件の並行ケースでは同じ seed・出力名・保存先候補を使い、呼び出しごとの結果と、衝突と掃除の後の成果物を照合する。エクスポーターは両評価器の実行履歴から得た操作順、結果、保存内容を比較し、同じ場合に JSON に書き出す。`--check` で生成済みの JSON と再生成結果を照合できる。Rust 実装のテスト用アダプターは、同じケースを実行して結果を JSON で返す。[照合データの仕様](../../../../spec/fixtures/README.md)

観測可能な契約を変更する場合は、対応するモジュールとシナリオを更新し、不変条件を確認してから実装に反映する。
